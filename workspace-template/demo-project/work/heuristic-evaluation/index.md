*Develop stage. An expert check of the final prototype against the project's principles, before any test with real users. It does not replace that test.*

> **Read first:** this is a draft by one evaluator (an AI tool that walked through the prototype). The levels are a starting point. Under the project's severity rules, ask at least three people to rate separately, then compare.

**Where the issues are:** the annotated screenshots below show every issue on the screen where it appears. Click a pin or an item in the list to jump between them. The viewer can also be edited (move pins, change a description or severity, add an issue) and exported.

## Scope
- **Product:** Travel Buddy, final interactive prototype, walked through at phone size.
- **Tasks checked:** first launch and sign-up (full path and "Explore without signing up"); the first tip; reading a trip in Plan; browsing people in Connect; reading and sharing a journal trip; changing settings.
- **Not walked through (yet):** the Map and Country views on Home, Discover more tips, Save to plan, sending a message, the Messages tab, notification, privacy and help settings, and log out.
- **Date:** 31 October 2026. **Evaluators:** one (AI draft); two more needed.

## Method
Each task was walked screen by screen and checked against the 10 principles in the project's Principle checks page, with severity rated 0 to 4 using frequency, impact and persistence together. The Principle checks page still has empty yes/no questions, so the questions used here are below, ready to copy back after the team agrees on them.

| Principle | Yes/no question used for this product |
|---|---|
| P1 Visibility of system status | Does the app show only what the traveller has chosen or done, with a clear reason for everything else it shows? |
| P2 Match with the real world | Do labels and content match how a traveller talks about a trip? |
| P3 User control and freedom | Can the traveller stop, pause, undo or leave at each step? |
| P4 Consistency and standards | Does the same word or action look and work the same everywhere? |
| P5 Error prevention | Does the app stop mistakes before they happen? (Not checked: no real inputs are validated in the prototype.) |
| P6 Recognition rather than recall | Can the traveller choose a person or place from what is on screen, without remembering a name? |
| P7 Flexibility and efficiency | Can a frequent task be done fast, with a short path and a way to skip what is not needed? |
| P8 Aesthetic and minimalist design | Is each screen free of what the task does not need? |
| P9 Help users recover from errors | When something goes wrong, does the screen say what happened and what to do next? |
| P10 Help and documentation | Is help easy to find when a traveller is stuck? |

## Top problems
1. **Finding a person (level 4, on record).** No search or filter in Connect, and sharing offers only three fixed people. Confirmed again in the current prototype.
2. **Browse mixes cities (level 3, on record).** People from other cities fill the list for a Chiang Mai trip.
3. **A state the traveller did not set (level 2, new).** A preselected "Near Me" destination, a trip and journals that already exist, and a capture banner for a trip never started. Confirm with the project owner which of these are deliberate sample data.

## Limits of this check
- **Sign-up is not a real test.** "Continue with Email" leads straight to "You're in!" with no email or password step. This is a limit of the prototype, not a usability problem to rate here.
- **One evaluator.** The levels are not yet an average of several people.
- **Heuristic only.** This check shows where a principle is broken, not whether real travellers understand the screens or finish their tasks. That needs the test with real people.
- **Not checked:** the items listed in Scope under "Not walked through (yet)".
